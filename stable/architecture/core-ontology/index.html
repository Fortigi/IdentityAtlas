    Core Ontology¶

    Identity Atlas stores a graph in PostgreSQL: five node tables (Systems, Principals, Resources, Identities, Contexts) and five edge tables (ResourceAssignments, ResourceRelationships, PrincipalRelationships, IdentityMembers, ContextMembers). Until now that graph had no written-down schema. The tables were in the migrations, the allowed values in the ingest validation, the meaning in comments and in several documentation pages, and they had drifted apart.

    The core ontology is that written-down schema: an OWL ontology in Turtle, ontology/core.ttl, in the namespace https://identityatlas.io/ontology#. It describes the model. It does not drive it: PostgreSQL stays the store, and no query, ingest path or screen reads the ontology at runtime.

    The human-readable version is the generated Core Model Reference. How to change it: Maintaining the Core Ontology.

    Three representations, one direction of truth¶

    flowchart LR
    subgraph impl["Application model (behaviour)"]
        MIG["Migrations<br/>tables, columns, CHECKs"]
        VAL["ingest/validation.js<br/>entity schemas, closed lists"]
        REG["lib/ownershipTypes.js, lib/resourceVisibility.js,<br/>effectiveAccess/engine.js, accountlinking/orphanQuery.js"]
    end
    ONT["ontology/core.ttl<br/>(description)"]
    DOCS["docs: core-model.md,<br/>data-model.md ERD"]
    VAL -- "unit check<br/>(npm run ontology:check)" --> ONT
    REG -- "unit check" --> ONT
    MIG -- "contract test<br/>(real PostgreSQL)" --> ONT
    ONT -- "generated<br/>(npm run ontology:generate)" --> DOCS
    • The implementation decides behaviour. When code and ontology disagree, the check fails and a human decides which one is wrong. The ontology never silently changes what the application does.
    • The ontology is the single description. Every table, column, type value and relationship type of the core model is in it, with a meaning.
    • Documentation is generated from the ontology where it describes the core model, and checked where it is hand-drawn. Nobody keeps a third copy in sync by hand.

    The checks read the code's own constants (SCHEMAS, RELATIONSHIP_TYPES, OWNERSHIP_RESOURCE_TYPES, …) — they never keep their own list of types. Where a list only existed inline, it was extracted to an exported constant that the code itself uses (CONTEXT_VARIANTS, CONTEXT_TARGET_TYPES, CONTEXT_MEMBER_ADDED_BY in validation.js, now also used by routes/contexts/shared.js).

    How the model maps to OWL¶

    Implementation Ontology Example
    Node table owl:Class, subclass of ia:Node, ia:table ia:Principal ↔ Principals
    Edge table (a row with its own columns) owl:Class, subclass of ia:Edge, with ia:sourceProperty / ia:targetProperty ia:ResourceAssignment ↔ ResourceAssignments
    Row identifier (id) the instance IRI — not a property (ia:identifierColumn, ia:identifierSqlType)
    Column property named exactly like the column, ia:sqlType = its PostgreSQL type Principals.accountEnabled → ia:accountEnabled
    Same column name on several tables one property, rdfs:domain is the owl:unionOf those classes ia:displayName
    Foreign-key column owl:ObjectProperty, range = the referenced class ia:managerId → ia:Principal
    Other column owl:DatatypeProperty, range from the SQL type (text → xsd:string, jsonb → rdf:JSON, …) ia:governed → xsd:boolean
    principalType (closed) / resourceType (open) subclasses with ia:typeValue; the parent has ia:discriminator (and ia:openVocabulary true when any value is accepted) ia:AIAgent ⊑ ia:Principal
    relationshipType value owl:ObjectProperty named lowerCamel of the value, with ia:typeValue, ia:storedIn the edge class, and the classes it connects as domain / range ia:hasAppRole: ia:Application → ia:AppRole
    Closed value list (assignmentType, origin, effect, variant, …) a class whose owl:NamedIndividuals are the values, named <List>_<value>; the column points at it with ia:valueScheme ia:AssignmentType_Direct
    A template (the level the application reasons at) a class with ia:template true between the kind of node and its types; a template with one built-in type is that type's own class ia:TechnicalRole, ia:Person, ia:Group
    What holding a resource reaches ia:expandsAccess true (membership expands) or false (a control permission never does), inherited by the types below ia:Group true, ia:ControlPermission false
    Ownership resources (lib/ownershipTypes.js) subclasses of ia:ControlPermission, each the range of exactly one ownership relationship ia:GroupOwnership
    The template of a context, stored the ia:ContextCategory value list, each value ia:denotesTemplate the template class; the contextCategory column ia:ContextCategory_OrganizationalUnit
    Who answers for a context ia:ContextRole: an edge from a context to an account or a person, role from ia:ContextRoleType (Accountable, at most one; Responsible, many) Piet is Accountable for his team
    Two contexts linked ia:ContextRelationship, relationship type ia:sameUnitAs (symmetric) Contoso's people ↔ Contoso's resources
    Who answers for an account the ia:Accountability value list (Personal, Shared, Autonomous), with ia:accountabilityDefault per principal type; declared ahead of its column ia:User → Personal
    contextType (open) subclasses of ia:Context named <Value>Context, with ia:typeValue, ia:producedBy (the plugin, if one emits it) and ia:allowedTargetType (the ia:EntityKind values it may group) ia:ManagerHierarchyContext

    Every term carries rdfs:label, rdfs:comment and rdfs:isDefinedBy <https://identityatlas.io/ontology>. The mapping annotations (ia:table, ia:sqlType, ia:typeValue, …) are owl:AnnotationProperty, so OWL reasoners ignore them and standard tools load the file unchanged.

    Why edges are classes. An assignment has fields (assignmentType, governed, origin, …). In RDF that means the edge becomes a node of its own — the "edge-with-fields" pattern. The relationship-type properties (ia:contains, ia:owner, …) are the direct shortcut between the two end nodes and say which classes each type connects; the edge class says where the row is stored.

    What the ontology does not say. Nullability, keys, indexes, materialised views, history and soft-delete mechanics, which keys appear inside extendedAttributes, and the contextType values that only a crawler or an analyst chooses. Those are either physical design (the migrations own them) or data-dependent (a future per-install layer, below).

    Three layers, one way of holding¶

    The model separates what exists, how things relate and who holds what. The first two may grow as rich as the sources need; the third never does. That is what lets the ontology describe group ownership, agent ownership and business roles while every matrix cell keeps the same three values.

    Layer What it describes May grow? Where
    Things Accounts, resources, persons, groupings, systems; their types (the source's word) and templates (what the product does with them) Yes; open vocabularies stay open the node classes and their subclasses
    Structure How things relate: resource to resource (Contains, HasAppRole, HasOwnership …), account to account (Owner, Sponsor), person to account, grouping to member By a closed, extendable list of relationship types the edge classes and the relationship-type properties
    Holding Who holds which resource, and how No. assignmentType is exactly Direct, Indirect or Eligible; governed and origin are flags on it ia:ResourceAssignment only

    The rule: a new kind of right is a new resource plus a relationship to what the right is about. It is never a new way of holding. So "owner of the group" is a resource of its own (GroupOwnership, a control permission), reached from the group through HasOwnership; Piet holds it Direct, or Eligible through PIM for Groups, like anything else. Owner and member refer to the same group through that link, not through the assignment. The only behaviour ownership has of its own is that holding it never makes the holder a member of what it controls: ia:expandsAccess false.

    Concept Things Structure Holding
    Member of a group Group — Direct
    Member through a nested group Group Contains between the groups Indirect
    Owner of a group GroupOwnership (control permission) HasOwnership from the group Direct
    Eligible directory role EntraDirectoryRole (technical role) — Eligible
    Business role granted BusinessRole Contains the groups it bundles Direct, governed
    Azure role inherited from a higher scope AzureRoleAssignment Contains between the scopes Indirect
    App consent DelegatedPermission / ApplicationPermission DelegatesScope / HasApplicationPermission from the app Direct
    Requested and approved — — a flag: origin = Requested
    An AI agent acting for a person AIAgent, accountability Personal Owner link agent → person —
    Member of a team an OrganizationalUnit context ContextMembers —
    Manager of a team an OrganizationalUnit context ContextRoles: Accountable —
    The resources that belong to a team a second OrganizationalUnit context, of resources ContextRelationships: SameUnitAs —

    Templates are the level the application reasons at: three for accounts (Person, Software, Agent), seven for resources (Group, TechnicalRole, Permission, Application, Scope, BusinessRole, Other) and four for contexts (OrganizationalUnit, LogicalApplication, Tag, Segment). Accounts have a second axis, accountability (Personal, Shared, Autonomous): a property of each account with a default per type; an AI agent's stays unknown until the source, an Owner or Sponsor link, or a person settles it. The ontology declares the templates, the defaults and the holding rule now (2.0.0); the columns that carry a template and an accountability per row, and the removal of the six root context types and of ExternalUser, follow in later pull requests.

    Scope¶

    In: the five node and five edge tables above, every column of them, every closed value list the ingest or the database enforces on them, every relationship type, every principal type, the resource types the application's own code branches on (ownership, business role, group, the Entra application family, directory roles), every type under exactly one template, and every type value something built in writes: what each crawler declares in its manifest's emits block (ia:emittedBy), what each context-algorithm plugin emits (ia:producedBy), and every context type a route or screen compares against. Which crawlers also pass free values through from source data is recorded too (ia:passthroughFrom).

    Out, for now — each is declared with a reason in ontology/validation.json, so a new ingest entity type cannot silently fall outside the model:

    • the governance satellite tables (GovernanceCatalogs, AssignmentPolicies, AssignmentRequests, CertificationDecisions) — business roles themselves are in the core, as Resources;
    • PrincipalActivity and RiskScores;
    • the values a source passes through: whatever a CSV file, a SQL statement or an Omada / midPoint mapping calls its resource and context types. Those are exactly what the dynamic layer is for.

    Contexts and the manager hierarchy, as implemented¶

    Verified against the code and its tests, not against earlier design documents.

    • One kind of member per context. targetType (Identity, Resource, Principal, System) is set on the context; every ContextMembers row of it has that memberType. A plugin has one fixed targetType and the runner stamps it on everything it writes — which is why accounts-by-system and resources-by-system are two plugins. Each context type in the ontology lists the kinds it may group (ia:allowedTargetType); the check compares that with every plugin.
    • One tree per hierarchy, through parentContextId. There is no second hierarchy mechanism. The tree is acyclic: the routes and the plugin runner refuse a closing link (cycleGuard.js), and a deferred trigger (trg_Contexts_reject_cycle, migration 059) aborts any transaction that commits a cycle. A child has the same targetType as its parent — the manual routes check it, plugin trees are same-type by construction, tags get one root per targetType — but the database and the ingest do not (finding 11).
    • The manager-hierarchy plugin (contexts/plugins/manager-hierarchy*.js) builds one tree per system of accounts (targetType Principal, contextType ManagerHierarchy, variant generated):
      • one node per manager referenced by Principals.managerId, plus a synthetic root with externalId root;
      • the manager is stated as the node's Accountable context role (since 2.1.0; before, only as the node's externalId, which still holds the manager's Principal id and which the member-move route reads);
      • members are the manager's direct reports, after analyst overrides (ManagerHierarchyOverrides); a manager is a member of their own manager's node, not of their own;
      • a node's parent is its manager's own manager's node, else the root; an account with no manager that manages nobody is a member of the root; a top-level manager is a member of no node;
      • a managerId that points at no account of the system still becomes a node, named Unknown;
      • a reporting loop (including an account that is its own manager) reaches the runner as a cycle; the runner keeps all but the closing link, so one node of the loop has no parent and the loop hangs outside the synthetic root;
      • every node carries contextCategory = OrganizationalUnit; the member-move route, the org-chart route and the matrix sort recognise the tree by the plugin that built it, not by its type.

    Pinned by manager-hierarchy.helpers.test.js ("irregular reporting lines"), runner.refresh.test.js and the runnerCycle / contextAcyclicTrigger contract tests; described on ia:ManagerHierarchyContext.

    Inconsistencies found¶

    Found while writing the ontology. None is fixed here — this feature describes, it does not change behaviour — except stale documentation. The implementation-side ones are recorded as known gaps in ontology/validation.json, so the check passes today and fails when one is fixed without removing its entry (the list only shrinks).

    1. contextId is still accepted by the ingest on principals, resources and identities, but the columns were dropped by the v6 Contexts redesign (migration 018). The value ends up in extendedAttributes.
    2. Contexts have no manager columns. validation.js, normalization.js and the data-model page say a context carries managerId / managerIdentityId; the table has neither, so managerExternalId / managerIdentityExternalId on a context never resolve. routes/riskScores/list.js (the contexts entity type) still selects Contexts.managerId, department and memberCount, none of which exist — that query fails at runtime.
    3. ContextMembers.memberId is a uuid, Systems.id an integer, yet memberType / targetType admit System. A System member cannot reference its system; routes/contexts/read.js compares the two as text, which never matches.
    4. policyId is validated as free text by the ingest but is a uuid column, so a non-uuid policy id passes validation and fails at insert.
    5. IdentityMembers has no extendedAttributes column, but the ingest accepts the field.
    6. ResourceRelationships.relationshipType has no CHECK constraint — only the ingest enforces the list — while assignmentType, origin and PrincipalRelationships.relationshipType are enforced by both. principalType likewise has no CHECK.
    7. GrantsAccessTo is called "reserved / not yet emitted" in CLAUDE.md and the ingest API page, but the CSV and SQL connectors emit it and the demo dataset uses it.
    8. Systems.resourceTypes / assignmentTypes exist and are never read or written.
    9. The same lists are kept by hand in crawler code: tools/crawlers/mssql/wizardLogic.js (PRINCIPAL_TYPES, RELATIONSHIP_TYPES, CONTEXT_TARGET_TYPES), SqlCrawler.Functions.ps1 ($SqlRelTypes, $SqlContextTargetTypes) and the SQL crawler's crawler.json enum. They are subsets today and nothing keeps them in step.
    10. Stale documentation, fixed here: the data-model ERD showed linkedAt on IdentityMembers (it is on Identities only), typed extendedAttributes as TEXT and riskScore as decimal (they are jsonb and integer), and omitted PrincipalRelationships; the PrincipalActivity section named columns (lastActivityDateTime, activityCount, a systemId key) the table does not have.

    Found while adding the context types (version 1.1.0). Again none of the behavioural ones is changed:

    1. The same-targetType rule for a parent and child context is not enforced by the database or the ingest. bootstrap.js calls it an invariant and the manual routes check it, but parentExternalId on ingested contexts is resolved without comparing target types.
    2. Deleting a generated node deletes the manual children under it. parentContextId is ON DELETE CASCADE; the runner's header comment said manual children survive (corrected here).
    3. Two spellings for an org unit. The ad-ou-from-dn plugin writes OrganisationalUnit; the Omada, CSV and midPoint crawlers write OrgUnit. Nothing branches on either today. Both are now defined (1.2.0), as the two different things they are: synced org units of persons, and OUs derived from accounts' distinguished names.
    4. The demo dataset types the Azure subscription AzureScope, while the Azure RM crawler writes AzureSubscription (and the demo never writes AzureManagementGroup), so the demo data looks unlike a real Azure crawl.
    5. Omada defines a resource-type map that is never applied. resourceTypeToIdentityAtlas in Start-OmadaCrawler.ps1 is declared, but ConvertTo-AtlasResourceType is never called; resource categories come from resourceCategoryMapping instead.
    6. The CSV crawler scopes its principal reconcile to principalType='User' even when its rows carry other types.
    7. Two "non-human account" lists. NON_HUMAN_PRINCIPAL_TYPES (account linking) is ServicePrincipal, ManagedIdentity, AIAgent; riskscoring/engine.js keeps its own inline list that also includes WorkloadIdentity.
    8. WorkloadIdentity and SharedMailbox are accepted but no built-in crawler emits them. They arrive only through CSV, SQL, SCIM or midPoint mappings; the Entra crawler deliberately does not classify workload identities.
    9. A stale code comment, corrected here: buildMemberRows said reports of a manager missing from the dataset go to the root; they stay together under an Unknown node.

    Future: dynamic ontology extensions¶

    Not built. The core is designed so that it never has to change for them.

    Two layers, never mixed.

    Core Dynamic extensions
    Lives in ontology/core.ttl, in Git the database (one Turtle document per extension, with status and provenance)
    Namespace https://identityatlas.io/ontology# per install, e.g. https://identityatlas.io/ext/<installId>#
    Changed by a pull request, gated by CI a user approving a proposal (from a wizard or a local LLM)
    Defined by rdfs:isDefinedBy <https://identityatlas.io/ontology> rdfs:isDefinedBy the extension's own ontology IRI, which owl:imports the core version it was made against

    What an extension may say. New subclasses of core classes (ext:SAPRole rdfs:subClassOf ia:Resource ; ia:typeValue "SAP Role"), new contextType classes under ia:Context, properties for keys inside extendedAttributes (an annotation such as ia:jsonKey "risk" would map them), labels and descriptions of its own terms. What it may not: declare a term in the core namespace, or add any triple whose subject is a core term. The same integrity checks plus that one rule gate every proposal before a user can approve it, so an approved extension cannot alter the core.

    Effective ontology = core ∪ approved extensions, merged as RDF graphs. Core-only, dynamic-only and combined views fall out of filtering on rdfs:isDefinedBy; the Mermaid and reference generators already take a parsed model, so they draw any of the three without change. An effective-ontology export (Turtle, plus RDF/XML for tools that need it) would be the first API endpoint, behind the existing data-export permission. The background proposal's "type registry" (ingest recording which resource types, context types and attribute keys each system produced) is the natural data source for the proposals.

    Export¶

    The artifact is the Turtle file in the repository, readable by Protégé, rdflib, Apache Jena or any RDF/OWL tool, also linked from the reference page as a raw download. There is deliberately no API endpoint yet: the core ontology is the same for every install, so serving it from the app adds nothing until per-install extensions exist. The namespace IRI is not dereferenceable today; publishing core.ttl at https://identityatlas.io/ontology is an open decision.

    The Ontology, Visually¶

    Identity Atlas keeps its data in PostgreSQL tables. The ontology describes what that data means: which kinds of things exist (an account, a group, a person, a team), how they may be connected, and which values a field may hold. It is the grammar of the data model, written in a standard format that other tools can read.

    This page shows what that looks like: first the overall picture, then one small team as real data, then a few lines of the schema file itself.

    Download the schema file

    The ontology is one file, core.ttl (view on GitHub). It is written in Turtle, the readable text format for RDF, and uses the OWL 2 vocabulary for classes and properties. Protégé, WebVOWL, Apache Jena, rdflib and any other RDF/OWL tool can open it; see Open it in a tool.

    The worked example on this page is a file too: examples/team.ttl.

    The big picture¶

    Everything in Identity Atlas is one of five kinds of node, connected by five kinds of edge. A solid arrow is an edge table: a row in it connects two nodes, and carries fields of its own (an assignment has an assignmentType, for example). A dotted arrow is a plain reference from one node to another (a column such as managerId).

    Node What it is
    System A source the data came from: Entra ID, Omada, a SQL database, a CSV file.
    Principal An account in one system: a user, a service principal, a managed identity, an AI agent, a guest.
    Resource Anything that gives access: a group, an app role, a directory role, a permission — and also a business role.
    Identity A real person, who may have accounts in several systems.
    Context A grouping of one kind of node: a team, a department, an OU, a tag, a cluster. Contexts form trees.

    Each kind has types below it. A Principal is a User, an AIAgent, a ServicePrincipal …; a Resource is a Group, an AppRole, a BusinessRole …; a Context is a ManagerHierarchy node, a Department, a Tag …. The next section shows them all.

    The types¶

    Each kind of node has types: a value in its type column (principalType, resourceType, contextType) that says what sort of account, resource or grouping a row is. Above the types sit 14 templates: three kinds of account (Person, Software, Agent), seven kinds of resource (Group, TechnicalRole, Permission, Application, Scope, BusinessRole, Other) and four kinds of grouping (OrganizationalUnit, LogicalApplication, Tag, Segment). The diagrams below show every type the ontology defines, grouped by its template: the level at which Identity Atlas reasons about it. The type is the source's own word; the template says what the product does with it. The small text under a type names the crawlers and plugins that write it.

    Account types (Principal)¶

    principalType is a closed list: the ingest accepts only these values. Crawlers that map types from their source (Omada, midPoint, SCIM, CSV, SQL) map onto this list. The template says what kind of actor an account is. Who answers for it is a second axis, accountability: Personal, Shared or Autonomous, a property of each account with a default per type. An AI agent can be any of the three (a personal assistant, a team assistant, an agent on its own permissions), so its default is unknown until the source, an Owner or Sponsor link, or a person settles it.

    Resource types (Resource)¶

    resourceType is an open list: any value is accepted, because every system names its own kinds of access. Defined here are the values Identity Atlas itself writes or relies on. The dotted arrow names the crawlers that also pass values through from their source data or configuration.

    Owning a group is a right in the target system, so it is a Permission of the control kind: a right over another object, which it names through the HasOwnership link from that object. Holding it never makes the holder a member of what it controls. That is how owner and member of one group stay two rows of the same group in the matrix, each held Direct, Indirect or Eligible.

    Grouping types (Context)¶

    contextType is an open list too, and since 2.1.0 every row also carries its template in contextCategory. A context groups one kind of node; the Core Model Reference lists which kind each type groups. OrgUnit (synced from an IGA or HR source, grouping persons) and OrganisationalUnit (derived by a plugin from accounts' AD distinguished names) are two values under the same template. A tree's root is simply a context without a parent, not a type of its own.

    An organizational unit or a logical application can say who answers for it: one Accountable (its manager or owner) and any number of Responsible people, each an account or a person. That is a link from the grouping to the person (ContextRoles), never access: nobody gains anything by being accountable for a team. Two org units can be two sides of one unit, the persons and the resources that belong to them, linked as two variants of one unit by SameUnitAs.

    One team, as data¶

    The picture below is a small, fictional team: Anna works for Piet. Anna has an account in Entra ID, holds a business role, and through a group has access to an app role. An AI agent holds that same app role directly. The manager-hierarchy plugin has put Anna in Piet's team.

    How to read it:

    • Colour = kind of node: purple a person (Identity), blue an account (Principal), green something that gives access (Resource), orange a grouping (Context). The grey box is the system the accounts and resources come from. The small text under each name is its type.
    • A solid arrow labelled Direct / Indirect is an assignment: who holds what, and how. Anna holds the business role Direct and governed (an approved request); she has the app role Indirect, because it comes through her group.
    • A thick arrow is a relationship between two resources: the business role Contains the group, the application HasAppRole the app role.
    • A dotted arrow is a reference: Anna's account names Piet's as its managerId; Piet's team sits below the organisation root (parentContextId).
    • Anna (the person) and anna.devries@example.org (the account) are two different things. The person can have more accounts in other systems; the identity member arrow links them.
    • Piet answers for the team. The Accountable arrow is a context role: the manager-hierarchy plugin states who is accountable for each node, and an analyst can add who is responsible. It is a link from the team to the person, not access; see Contexts and the manager hierarchy.

    The same team, as the file says it¶

    This is the complete example file. Every word after ia: is a term from the ontology. Each block describes one thing: its type after a, then its fields.

    # Worked example: one small team, described with the Identity Atlas core ontology.
#
# Fictional people and systems. Every resource below is an instance of a class
# from ontology/core.ttl, and every property is one of its terms — this is
# what the data in an Identity Atlas database looks like when it is written as
# RDF. `npm run ontology:check` (app/api) validates this file against the
# ontology, and the picture on docs/concepts/ontology.md is generated from it,
# so neither can drift from the model.
#
# Rows of the edge tables (assignments, identity and context memberships) are
# resources of their own, because they carry fields. A resource-to-resource
# relationship (Contains, HasAppRole …) is written as the direct shortcut
# property between the two resources.

@prefix ia: <https://identityatlas.io/ontology#> .
@prefix ex: <https://identityatlas.io/example#> .

# ── A source system ──────────────────────────────────────────────────────────
ex:entra a ia:System ;
    ia:displayName "Entra ID" .

# ── Two people and their accounts ────────────────────────────────────────────
ex:anna a ia:Identity ;
    ia:displayName "Anna de Vries" .

ex:annaAccount a ia:User ;
    ia:displayName "anna.devries@example.org" ;
    ia:systemId ex:entra ;
    ia:managerId ex:pietAccount .

ex:pietAccount a ia:User ;
    ia:displayName "piet.jansen@example.org" ;
    ia:systemId ex:entra .

ex:annaIsAnna a ia:IdentityMember ;          # account correlation: this account is Anna
    ia:identityId ex:anna ;
    ia:principalId ex:annaAccount .

# ── An AI agent that holds access as its own account ─────────────────────────
ex:plannerBot a ia:AIAgent ;
    ia:displayName "Planning assistant" ;
    ia:systemId ex:entra .

# ── What can be held ─────────────────────────────────────────────────────────
ex:planningGroup a ia:Group ;
    ia:displayName "SG-Berth-Planning" ;
    ia:systemId ex:entra .

ex:plannerRole a ia:BusinessRole ;            # a governance construct (access package)
    ia:displayName "Berth planner" ;
    ia:systemId ex:entra ;
    ia:contains ex:planningGroup .

ex:berthApp a ia:Application ;
    ia:displayName "Berth Planning System" ;
    ia:systemId ex:entra ;
    ia:hasAppRole ex:berthPlanner .

ex:berthPlanner a ia:AppRole ;
    ia:displayName "Planner" ;
    ia:systemId ex:entra .

# ── Who holds what (rows of ResourceAssignments) ─────────────────────────────
ex:annaHoldsRole a ia:ResourceAssignment ;
    ia:principalId ex:annaAccount ;
    ia:resourceId ex:plannerRole ;
    ia:assignmentType "Direct" ;
    ia:governed true ;
    ia:origin "Requested" .

ex:annaInGroup a ia:ResourceAssignment ;
    ia:principalId ex:annaAccount ;
    ia:resourceId ex:planningGroup ;
    ia:assignmentType "Direct" .

ex:annaHasAppRole a ia:ResourceAssignment ;   # through the group: Indirect
    ia:principalId ex:annaAccount ;
    ia:resourceId ex:berthPlanner ;
    ia:assignmentType "Indirect" .

ex:botHasAppRole a ia:ResourceAssignment ;
    ia:principalId ex:plannerBot ;
    ia:resourceId ex:berthPlanner ;
    ia:assignmentType "Direct" .

# ── The team, as the manager-hierarchy plugin builds it ──────────────────────
ex:orgRoot a ia:ManagerHierarchyContext ;
    ia:displayName "Organisation" ;
    ia:targetType "Principal" ;
    ia:contextCategory "OrganizationalUnit" ;
    ia:variant "generated" ;
    ia:externalId "root" .

ex:pietsTeam a ia:ManagerHierarchyContext ;
    ia:displayName "Berth Planning (Piet Jansen)" ;
    ia:targetType "Principal" ;
    ia:contextCategory "OrganizationalUnit" ;
    ia:variant "generated" ;
    ia:externalId "pietAccount" ;
    ia:parentContextId ex:orgRoot .

ex:pietAnswersForTeam a ia:ContextRole ;        # who answers for the team: a link, not access
    ia:contextId ex:pietsTeam ;
    ia:principalId ex:pietAccount ;
    ia:role "Accountable" ;
    ia:addedBy "algorithm" .

ex:annaInPietsTeam a ia:ContextMember ;
    ia:contextId ex:pietsTeam ;
    ia:memberId ex:annaAccount ;
    ia:memberType "Principal" ;
    ia:addedBy "algorithm" .

    What the schema file says¶

    The ontology itself is written the same way, but it describes the kinds of things instead of the things. A few excerpts, quoted straight from core.ttl:

    A kind of node. ia:Principal is a class. It is stored in the Principals table, and its principalType column says which subtype a row is:

    ia:Principal a owl:Class ; rdfs:subClassOf ia:Node ;
    rdfs:label "Principal" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "An account in a source system: a user, service principal, managed identity, AI agent, guest, shared mailbox …" ;
    ia:table "Principals" ; ia:identifierColumn "id" ; ia:identifierSqlType "uuid" ; ia:ingestEntity "principals" ;
    ia:discriminator "principalType" ;
    ia:passthroughFrom "csv", "custom-connector", "midpoint", "mssql", "omada", "scim" .

    A type below it. An AI agent is a Principal whose principalType is AIAgent:

    ia:AIAgent a owl:Class ; rdfs:subClassOf ia:Agent ; ia:typeValue "AIAgent" ;
    ia:emittedBy "demo", "entra-id" ;
    rdfs:label "AI agent" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "An AI agent (Copilot Studio, Azure OpenAI, a custom bot) that holds access as its own account." .

    A context type, with the plugin that makes it and the kind of node it groups:

    ia:ManagerHierarchyContext a owl:Class ; rdfs:subClassOf ia:OrganizationalUnit ; ia:typeValue "ManagerHierarchy" ;
    ia:producedBy "manager-hierarchy" ; ia:allowedTargetType ia:EntityKind_Principal ;
    rdfs:label "Manager hierarchy node" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "One generated context per manager of one system's accounts, plus a synthetic root (externalId 'root'). The manager is recorded only in externalId, which holds the manager's Principal id — there is no manager column or member role. Members are the manager's direct reports (Principals.managerId, overridden per account by ManagerHierarchyOverrides); the manager is a member of their own manager's node, not of their own. parentContextId is the node of the manager's own manager, else the root. Accounts with no manager that manage nobody are members of the root; a top-level manager is a member of no node. A managerId that points at no account of the system still becomes a node, named 'Unknown'. A reporting cycle, a self-reference included, leaves a node without a parent: the runner refuses the link that would close the cycle." .

    A relationship type between two resources, and which classes it connects:

    ia:hasAppRole a owl:ObjectProperty ; ia:typeValue "HasAppRole" ; ia:storedIn ia:ResourceRelationship ;
    rdfs:domain ia:Application ; rdfs:range ia:AppRole ;
    rdfs:label "has app role" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "An application and one of its app roles." .

    A closed list of values. An assignment is always one of exactly three:

    ia:AssignmentType a owl:Class ;
    rdfs:label "Assignment type" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "How an assignment is held. Only these three values exist; ownership, governance and source detail are modelled elsewhere." .
ia:AssignmentType_Direct a owl:NamedIndividual, ia:AssignmentType ; ia:typeValue "Direct" ;
    rdfs:label "Direct" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "Held directly: a membership, a directly assigned app role, an OAuth2 grant, an ownership." .
ia:AssignmentType_Indirect a owl:NamedIndividual, ia:AssignmentType ; ia:typeValue "Indirect" ;
    rdfs:label "Indirect" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "Inherited through another resource (an app role held via a group, a nested group). Stored, not inferred." .
ia:AssignmentType_Eligible a owl:NamedIndividual, ia:AssignmentType ; ia:typeValue "Eligible" ;
    rdfs:label "Eligible" ; rdfs:isDefinedBy <https://identityatlas.io/ontology> ;
    rdfs:comment "Granted but not active (PIM-eligible): can be activated." .

    Every term carries a label and a description; the Core Model Reference lists them all as tables, generated from this same file.

    One way of holding¶

    The model separates what exists (the types and templates above), how things relate (the relationship types) and who holds what. The first two may grow. The third never does: an account reaches a resource only through an assignment, held Direct, Indirect or Eligible. A new kind of right, such as owning a group, is a new resource plus a relationship to the object it is about, never a new way of holding. That rule is what keeps every matrix cell to three values while the ontology grows; Core Ontology has the full table of concepts and where each one lives.

    How it stays true¶

    A description is only useful if it matches the application. Three things keep it that way:

    • CI compares the ontology with the code. If a developer adds a relationship type, a principal type, a column, a context type or an allowed value without describing it, the build fails. It also fails the other way round, when the ontology describes something the code does not do.
    • CI compares it with the database. A database migrated from scratch must have exactly the columns and allowed values the ontology describes.
    • The pictures on this page and the reference page are generated from the ontology, and the example file is validated against it. Nobody draws them by hand, so they cannot drift.

    The details, and what is deliberately not checked, are on Core Ontology. How to change the model: Maintaining the Core Ontology.

    Open it in a tool¶

    • Protégé (free desktop editor, protege.stanford.edu): File → Open from URL, paste the core.ttl link above. The Entities tab shows the class tree (Node → Principal → AIAgent …) and every property with its domain and range. The OntoGraf tab draws it.
    • WebVOWL (in the browser, service.tib.eu/webvowl): download core.ttl, then Ontology → Select ontology file to see an interactive graph of the classes.

    • Python (rdflib):

      from rdflib import Graph
g = Graph().parse("https://raw.githubusercontent.com/Fortigi/IdentityAtlas/main/ontology/core.ttl")
for cls in g.query("""
    PREFIX ia: <https://identityatlas.io/ontology#>
    PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
    SELECT ?type WHERE { ?c rdfs:subClassOf ia:Principal ; ia:typeValue ?type }"""):
    print(cls.type)          # User, ServicePrincipal, AIAgent, …

    The namespace https://identityatlas.io/ontology# is an identifier, not a web page: opening it in a browser does not return the file. Use the download links above.

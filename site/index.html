Why we built it

The information already exists. The clarity doesn't.

Sound familiar? You've invested in a capable IGA system — and your analysts still export to Excel to actually make sense of it. The data isn't missing. A way to see it is.

Fragmented

Azure RBAC, Entra ID and Azure DevOps each answer “who has access” in a different place, in a different way.

Invisible

Over-privileged accounts, eligible-but-unused PIM roles and never-reviewed access hide in the gaps between systems.

Unprovable

“Who could do what last quarter?” is guesswork once memberships change — there's no reliable timeline.

The real problem

It's not about finding one needle — that's too narrow a question. It's about making sense of the whole haystack. Identity Atlas facilitates role mining and analytics, so analysts, support desks and resource owners can look at identity data from every angle and slice it whatever way fits the job in front of them.

What it is

Identity Atlas, in one view.

It syncs authorization data from every connected system into one model with full history, shows it in a visual access matrix, and scores identity risk — without any identity data leaving your environment.

Unified permission model

Every system's permissions in one PostgreSQL model — groups, roles, app roles, SharePoint, business roles alike — with full row-level audit history.

Visual access review

Role mining and a visual access matrix — slice by user, role, resource or system, and see the exact route each grant took: direct, group, owner, eligible (PIM), governed, app-role. Built for the way analysts, support desks and resource owners actually think.

Identity risk scoring

A defensible score per identity — privacy-preserving and LLM-assisted, using public org context only. An optional layer you switch on when you want it.

Multi-system & open

Entra ID natively; Azure RBAC, Azure DevOps, plus Omada, SailPoint and any CSV for the rest. MIT-licensed and self-hosted.

How to start

Pick a release channel. Pick a way to run it.

Everything ships as a self-contained stack. Evaluate in minutes; run it wherever you run containers, or one-click into your own Azure.

Edge

Bleeding-edge dev builds. Docker tag :edge, pushed on every merge to main.

Beta

Pre-release builds. Docker tag :beta — try what's next before it's stable.

Stable

Released versions. Docker tag :latest and pinned Major.Minor.Patch.0. Recommended for production — pin it and pull on your own schedule.

Docker stack

Fastest to evaluate. docker compose up, open localhost:3001. Self-host anywhere you run containers. One-click demo data — no tenant needed.

One-click to Azure

Into your own subscription. PaaS-only, deploys in ~15 minutes. Entra SSO enforced — no anonymous access. From ~€45/mo for a proof-of-concept.

Portable Windows launcher

For locked-down laptops. No install, no admin rights, no Docker — runs from a folder. Good for a quick, contained look.

bash — evaluate in under a minute 
# Grab the compose file and start the stack
curl -O https://raw.githubusercontent.com/Fortigi/IdentityAtlas/main/docker-compose.prod.yml
docker compose -f docker-compose.prod.yml up -d --pull always
# open http://localhost:3001 → Admin → Crawlers → Add Crawler

Why you can trust it

Built to be inspected, not taken on faith.

Identity Atlas reads authorization data and keeps it inside your walls. Here's what backs that up.

Your infra, your cloud

Self-hosted end to end; runs entirely inside your environment. Deploy to your own Azure subscription — nothing runs on Fortigi infrastructure.

Read-only by design

Identity Atlas reads authorization data. It never changes anything in your source systems.

Inspect the code — MIT

Open to read, fork, challenge and contribute. Adopting it means forking the MIT repo, so all code lives inside your tenant. You control updates.

LLM is optional, public context only

Risk scoring is an optional layer you switch on. When you do, the model profiles your org from public-domain information only — no identity data is ever sent to it.

Secrets encrypted

LLM keys and crawler credentials use AES-256-GCM envelope encryption, with a master key you control.

Auth on from first deploy

Entra SSO enforced on every endpoint. There's no anonymous, open state to leak into.

Extensive quality assurance

Unit tests (Vitest + Pester), enforced code-coverage ratchets, file-size & complexity gates, a duplication gate, Playwright E2E, and load/soak tests.

Supply-chain guarded

A published SBOM, Dependabot keeping dependencies current, and Socket Firewall vetting new packages against supply-chain attacks before they land. Built on PostgreSQL 16.

Built by a real team
